### Q-02 🟡 UI 外壳选型

**结论**：**以本地 Web UI 为主壳**（Python 标准库 `http.server` 提供 API + 静态页；单页应用，无前端构建、无 CDN）。

**理由（实测支撑）**
1. 翻译工具的 Web 壳已经成熟：21 条 API 路由（`tool/server.py:476-549`）、完整的后台任务与进度上报、678 行前端含一套可用的暗色设计令牌（`web/index.html:8-12`）。这是**现成资产**。
2. tkinter 侧的价值全在**逻辑层**（`engines.py` / `rpgdata.py` / `mvdata.py` / `rmarshal.py` / `lzstring.py` 共 1839 行），GUI 层（`main.py` 494 行）本身就是"取控件值→调 sf→刷控件"的胶水，重写成本低。
3. 需求 §4.4 要求"任务类操作必须有进度反馈、可中断"：tkinter 单线程 + `mainloop` 下做可中断的后台任务与进度条成本高；Web 壳已有成熟的 job 轮询范式（`web/index.html:490-541`）。
4. 零第三方依赖约束下，**没有任何可用的现代桌面 UI 库**（PyQt/PySide 全被禁止）；tkinter 是唯一选项，但它的样式能力**实测为零**——修改工具没有一行 `ttk.Style()` 调用，纯系统默认外观。用 tkinter 做"美观、风格统一"必然失败。
5. 混合方案（Web 主壳 + tkinter 弹原生对话框）**已经被原工具采用**（`tool/server.py:65-87` 用 tkinter 弹文件夹选择器），继续沿用即可，不需要额外决策。

**替代方案代价**
- **纯 tkinter 重写**：需把扫描/翻译/生成汉化版/字体/备份还原全部重做成 tk 控件；主题一致性只能靠 `ttk.Style` 手搓（无 CSS 令牌）；跨平台能力提升但用户是 Windows 优先。**代价：工作量最大，且直接牺牲 §4.4 的视觉要求。**
- **替换 Web 壳为第三方框架**（Flask/FastAPI）：违反 §4.1 零依赖，**直接否决**。

### Q-03 🟡 是否保留旧入口作为兼容层

**结论**：**彻底切换单入口**，不保留旧 `.bat` 作为兼容层。

**理由**
1. 需求 §4.3 硬约束"**不得原地修改**两个参考目录"——所以那两个 `.bat` **物理上保持不动**（它们继续可用，作为独立回退工具）。既然不能改，就不存在"兼容层"的实现空间。
2. 需求 §4.4 要求"单一入口、一次启动"。若在新工程里再放两个旧 `.bat` 转发，会与"统一工具"的定位矛盾。
3. 迁移映射与旧工具"仍可运行"这两件事**共同构成回退路径**，比一个转发脚本更可靠。

**代价**：用户若习惯双击旧图标，需要改用新脚本一次。`README.md` 里显式说明"旧工具仍在 `D:\test1\rpgtool\` 下，可继续单独使用"。

### Q-04 🟡 core 合并顺序与回退策略

**结论**：**分层推进——"先建壳→再物理合并→再抽象"**；粒度是**文件**，不是仓库。

**具体顺序**
1. **先建壳（M1）**：新工程建目录与 `manifest.py` 契约，`core/` 先放**薄包装**：直接 import 原实现（用 `sys.path` 指向参考目录）或复制过来。此时**不做任何抽象**，只要"能跑"。
   - 好处：M1 就能端到端启动，足迹校验可跑通，风险最低。
   - 关键手法：`core/engines.py` 这类**一开始就是一份新文件**，内部按需求组合两侧能力（判据并集 + 双目录返回），而不是先搬两份再合并。**这样从第一天起就不存在"两份引擎识别"。**
2. **再物理合并（M2）**：`marshal` 是唯一需要"真合并"的地方（两份各有独有能力）。策略见 Q-04b。
3. **最后抽象（M2 尾）**：抽出 `core/formats/jsoncodec.py`（JSON + LZString + zlib + 加密包装），让游戏数据路径与存档路径共用。

**回退策略**（三层，逐层更细）
| 层级 | 手段 |
| --- | --- |
| 最小 | 每个里程碑一个 git commit；`git revert` 单点回退 |
| 中 | 两个参考目录**原样保留且未被修改**（git 可验证 `git status` 干净）；新工程任何阶段都能原地对照 |
| 最大 | 参考目录**本身就是两套可运行的回退工具**，功能不缩水地独立存在 |

**Q-04b（marshal 合并方向，M2 执行细节）**：以**文档模型（`rmarshal.py`）为二进制层主体**，把值模型（`tool/marshal.py`）降为对象门面。理由：`Node.raw`/`dirty` 增量保真是字节级无损的**机制保证**（`rmarshal.py:103-116`），而值模型只靠"同序遍历"的自述约定（`tool/marshal.py:9-11`），遇到未知 token（`:418`）或浮点尾就失效。必须从值模型移植：`e`/`C`/`M`/`d` 四个 type code 的读写对称实现、字符串编码视图（旁挂字段，不参与写回）、对象门面 API（`loads_py`/`dumps_py`）；bignum 直接沿用文档模型的可写实现。
**先修后并**：`rmarshal.py:491-496`（被 `:508-510` 覆盖的重复 `_fixnum` 定义，导致 XP/VX 解析与写回编码不对称）必须先修，否则把字节漂移固化进新模块。

### Q-05 🟡 功能注册表形式：`module.json` vs `manifest.py`

**结论**：**`manifest.py`**（Python 数据结构），并用**显式 import 的自动发现**。

**理由**
1. 零第三方依赖 + Python 原生，`manifest.py` 可直接写 Python 表达式（如健康检查函数引用、依赖的 core 能力对象），`module.json` 只能写字符串再二次解析。
2. **可测试性**：`manifest.py` 能被 `tools/check_footprint.py` 直接 import 后断言（例如"声明的 `tests` 文件必须存在"），JSON 需要额外校验器。
3. **无循环依赖风险**：`manifest.py` 只放数据 + 一个 `register(ctx)` 注册函数签名，不做 import 副作用。

**自动发现机制（明确取舍）**
- 用 `pkgutil.iter_modules(features.__path__)` 枚举 `features/*`，对含 `manifest.py` 的目录 `importlib.import_module`。
- **不做隐式扫描魔法**：不允许"放个文件就生效"这种靠 import 副作用的行为。启动时必须能在日志里打印出"已加载的功能模块：translate, cheats"。
- 前端的"入口自动出现"：`ui/pages/registry.js` 里每个页面一个模块文件，`ui/app.js` 从一份 `PAGES` 清单渲染导航。**这一处登记是允许的**——需求 §5.1 明确"如果做不到自动发现，至少做到只在固定一两处登记"。后端自动发现 + 前端单点登记 = 两处，符合要求。

**替代方案代价**：`module.json` 需引入 schema 校验与字符串到对象的映射层，且无法在清单里声明 Python 侧的注册函数；收益（语言无关）在本项目不成立（无其它语言消费者）。

### Q-06 🟡 真实样本测试如何组织

**结论**：**三层分离——合成样本入库、真实样本仅本地、兼容性双跑。**

| 层 | 内容 | 位置 | 入库？ | 运行条件 |
| --- | --- | --- | --- | --- |
| **L1 合成层** | 用 Python **当场构造**最小样本（最小 marshal 字节流、合成 MV/MZ 工程目录树、合成 rvdata2），常规单元测试 | `<root>/tests/unit/` | ✅ 入库 | 任何机器，无外部依赖 |
| **L2 真实层** | 环境变量指定的真实游戏（`RPGTOOL_SAMPLES`），**只读**，逐引擎各 1 个样本的扫描/读档/写回副本 | `<root>/tests/local/` | ❌ 不入库 | `RPGTOOL_SAMPLES` 已设置 |
| **L3 兼容层** | 两个原工具的 roundtrip 断言合并后双跑同一批文件 | `<root>/tests/compat/` | 仅代码入库 | 需 L2 |

**规避版权与体积的具体做法**
1. **零游戏内容入库**：仓库内不出现任何游戏文本、`.rvdata2`、`.json` 数据文件。L1 的合成样本由代码生成，内容为测试用假文本（如 `"测试文本1"`）。
2. **样本清单只记元数据**：`tests/local/samples.json` 记录**路径 + 大小 + sha256**，不记录内容。这样"样本换过"能被发现（哈希不匹配即提示重新采集），但内容不泄露。
3. **API Key 不入库、不入日志**：`config.json` 进 `.gitignore`；`OPENAI_API_KEY` / `DEEPL_API_KEY` 走环境变量；日志打印前对 `api_key` 字段做掩码。
4. **`.gitignore` 增加**：`config.json`、`sessions/`、`*.bak`、`*汉化备份_*/`、`tests/local/samples/`。
5. **测试不得污染游戏目录**：所有写回测试必须在 `tempfile.mkdtemp()` 的副本上做（原工具的 `test_all_saves.py:25` 直接写在游戏目录里，**不迁移这种做法**）。

**替代方案代价**：把样本打包进 git-lfs 或 release 附件——引入外部依赖、体积不可控、版权风险，**否决**。

### Q-09 🟡 出网路径不做真实网络断言（已在 M3a/M3b 落地，请确认）

**背景**：`features/translate/translators.py` 里的 429 退避重试（3/10/30 秒）、
单批看门狗超时（默认 120s）、以及 Google / DeepL / OpenAI 兼容接口的响应解析
都是**出网路径**。需求 §8 的 8 项验收标准里没有要求"必须真的连上翻译服务"。

**结论**：**测试一律不出网**。保障方式改为四条：

1. 代码原样保留（vendored），契约写在 docstring 里；
2. 四个适配器必须**能被构造**（`test_providers_ids_match_build_translator`）；
3. 单批超时可在本地触发（`chunk_timeout`）；
4. 界面提供「接口自检」按钮，由**用户**在自己的网络环境里验证真实连通性。

**理由**
* 让它出网 = 测试会因为对方服务波动、限流、地区封锁而**间歇性红**，
  这种"红"会训练人忽略红灯 —— 比没有这条测试更糟（M3a 的教训：一个间歇性失败
  的用例差点被误判成业务缺陷）。
* 出网还会把"跑一次测试"变成有外部副作用的操作（打到第三方服务、可能计费）。
* 用户真正需要的"配置对不对"由自检按钮回答，而且**用他自己的密钥与网络**，
  比 CI 里的固定样例更准。

**代价**：响应解析的边界情况（截断、markdown 围栏、JSON 修复）只有单元级覆盖
（`translators.py` 里的 `_clean_json` / `_FENCE_RE` 等纯函数可测），
没有真实响应样本。如果评审认为这不够，建议的补法（**默认不跑**）：

* 新增 `tests/local/test_online_smoke.py`，只在显式设置
  `TUDOU_RPGTOOL_ONLINE=1` 时运行，且只打一次最小请求；
* 或在 `tests/local/` 放**脱敏后的真实响应样本**（JSON 片段），
  让解析路径可以离线回归 —— 这条不涉及出网，成本低，**推荐优先做这条**。

**需要确认**：接受"这类游戏没有图标"这个边界吗？如果要覆盖，
唯一现实的路是新增"手动指定 key"的输入框（让用户自己从游戏论坛抄 key），
成本不高但界面要多一个高级选项 —— 在此之前建议维持现状。

### Q-12 🟡 图标缓存的有效期：只在 `open_game` 时失效，够不够？（请确认）

**背景**：`CheatsService._icon_cache` 在 `open_game()` 里清空，
因此在"同一个游戏目录里把 IconSet 换掉、但不重新点『读取游戏数据』"的情况下，
界面会继续用旧图集。

**为什么先这样**：用户换图集的场景基本只有"我改了图集想看看效果"，
那种情况下重新点一次『读取游戏数据』是很自然的动作；而给每次
`/icon_set` 请求都加 `mtime` 校验会把"免除一次磁盘读"的收益抹掉大半
（虽然实测解密只要几毫秒，但没必要）。

**若认为不够**：改成按 `(路径, mtime_ns, size)` 做 key 的缓存即可，
`core/iconutil.py` 不动（它本来就是无状态的，缓存只在 service 层）。

### Q-13 🟡 「最近打开」显示目录名还是游戏标题？（请确认）

**背景**：F-09 的下拉里，每条目前显示**目录名**（`wdss2`、
`ToT 1.16.2.2 CN1.0`、`博麗霊夢は洗脳されてしまいました`）。

**为什么先这样**：目录名是用户自己在文件管理器里看到的那一层，**零解析成本、
永远可得**，也不会因为游戏数据表坏掉而拿不到。游戏标题要分引擎取
（MV/MZ 读 `System.json` 的 `gameTitle`，RGSS 读 `Game.ini` 的 `Title=`），
而这两处都可能缺、可能是空、可能是乱码 —— 那时候界面就得决定"显示什么"，
反而多一类边界。

**代价**：目录名认不出来时（例如一堆 `1.05正式版`、`PC-1`、`整合-1`），
用户可能要靠 `title` 里的完整路径才能分辨。

**建议**：先按目录名交付（已完成）。如果实际用起来不好认，再补标题 ——
做法是 `RecentGames.record()` 多收一个 `title` 字段，由两个功能的
`open_game` 在**已经读过数据表之后**顺手填（那时标题本来就是现成的，
不用额外解析）。不需要改存储结构（加字段即可，`schema` 已在文件里）。
